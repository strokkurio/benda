# Data layer: from OpenAPI spec to UI

How Angular apps built with Benda get their data, and how Benda's overlay helps to build that layer.
This document is both the team concept and the rule set the coding agents (Claude Code, OpenCode)
follow. The rules are Angular-specific.

## Goals

- **The UI never depends on the API's shape.** API changes are absorbed in one place (the mapper),
  not in every component.
- **Generated code stays generated.** Clients are regenerated from the spec, never edited by hand.
- **Loading, error and mutation handling are consistent** across features and micro frontends.
- **The overlay shows and builds this layer in the browser**, with AI proposals the developer confirms.

## The four layers

```
api/<name>/<version>.yaml ──generate──▶ ① API client      (generated: services + DTO types)
                                              │ DTOs
                                              ▼
                                        ② Mapper          (pure functions, DTO ↔ model, unit-tested)
                                              │ UI model
                                              ▼
                                        ③ Store           (one per domain: signals, loading/error, mutations)
                                              │ signals
                                              ▼
                                        ④ Components      (inject the store, render the model)
```

| Layer       | Lives in                                            | Rules                                                                                                                                                                                            |
| ----------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ① Client    | `projects/shared/api/<name>/` (alias `@api/<name>`) | Generated by orval or openapi-generator. Never edited. Committed so the app builds without the generator.                                                                                        |
| ② Mapper    | `<feature>/data-access/<entity>.mapper.ts`          | Pure functions `toX(dto)` / `toXInput(draft)`. Units (cents → euros), enums → labels, ISO strings → `Date`, null handling. Unit tests for every mapper.                                          |
| ③ Store     | `<feature>/data-access/<entity>-store.ts`           | `@Service()` class. Reads with `rxResource` over the generated client; exposes `computed` model signals, `isLoading`, `error`; mutations as `async` methods with optimistic update and rollback. |
| ④ Component | the feature                                         | Injects the store only. Never imports `@api/*`.                                                                                                                                                  |
| UI model    | `<feature>/data-access/<entity>.model.ts`           | Readonly interfaces in the UI's language, plus a `Draft` type for editable fields.                                                                                                               |

The store belongs to the micro frontend that owns the domain. Only the generated client is shared.

### Why `rxResource` and not `httpResource`

`httpResource` takes a URL and bypasses the generated client. Both generators produce services that
return `Observable`s; `rxResource` wraps them with the same signal API (`value()`, `isLoading()`,
`error()`, `reload()`, writable `value` for optimistic updates).

### Store template

```ts
@Service()
export class CustomerStore {
  private readonly api = inject(CrmApiService); // generated client

  readonly filter = signal<CustomerFilter>({});

  private readonly page = rxResource({
    params: () => this.filter(),
    stream: ({ params }) => this.api.listCustomers(params),
  });

  readonly customers = computed(() => (this.page.value()?.items ?? []).map(toCustomer));
  readonly isLoading = this.page.isLoading;
  readonly error = computed(() =>
    this.page.error() ? 'Customers could not be loaded.' : null,
  );

  async remove(id: string): Promise<void> {
    const previous = this.page.value();
    if (previous)
      this.page.value.set({ ...previous, items: previous.items.filter((c) => c.id !== id) });
    try {
      await firstValueFrom(this.api.deleteCustomer(id));
    } catch {
      if (previous) this.page.value.set(previous); // rollback
      // expose a user-facing error signal
    }
  }
}
```

### Mutations

- Optimistic for deletes and toggles. Wait for the server on creates and complex updates, then
  replace the item with the server's response.
- Errors become user-facing messages in the store (`error` signal). Components show them; they
  never inspect `HttpErrorResponse`.
- Validation rules for forms come from the spec schema of the request body (`required`, `maxLength`,
  `minLength`, `minimum`/`maximum`, `pattern`, `format: email`, `enum` → a select) and are mapped to Signal
  Forms or Reactive Forms validators. Validators in code and template attributes must agree.
- A form submits through a store mutation; a write mapper `toXInput(draft)` builds the request body, so
  every control's draft field reaches exactly one request field.

## Generators

Both are supported. Benda detects them from their configuration:

| Generator                                | Config Benda reads                                                                                                | Result                                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| orval (`client: 'angular'`)              | `orval.config.{ts,js,mjs,cjs}` (`input` / `output.target`)                                                        | one `@Injectable` service per spec (or per tag), DTO types in `model/`           |
| openapi-generator (`typescript-angular`) | `openapitools.json` (`generator-cli.generators.*`) or npm scripts with `openapi-generator-cli generate -i … -o …` | `*Service` classes per tag, models, `Configuration`/`BASE_PATH` for the base URL |

Base URL: generate relative URLs under `/api` (orval `baseUrl: '/api'`, openapi-generator `BASE_PATH`
provider) and proxy `/api` in the dev server (`proxy.conf.json`), so every micro frontend – inside the
shell or standalone – reaches the same backend or mock.

## Specs and versions

- Specs live below `api/` (configurable as `api.dir` in `benda.config.json`). Any layout
  works; Benda finds every YAML/JSON file that is an OpenAPI or Swagger document.
- Recommended layout for versions: `api/<name>/<info.version>.yaml`. The API tab stores new
  versions this way and shows what changed against the previous one (operations, schemas, fields).
- The generator config decides **which version is generated**; the API tab marks it (●) and can
  re-run the generator.
- Before moving to another version, the API tab's **Impact on the app** lists what it means for the code
  (see below). After regenerating, the compiler and `npx benda check` show what is still left.

## Mocks

`npm run dev` starts every entry in `api.mocks`. There are two kinds:

- `{ "spec": "api/crm/1.1.0.yaml", "port": 4010 }`: `@stoplight/prism-cli` serves the spec's `example`s.
  The answers are static, so query parameters (search, filters, paging) and mutations have no visible
  effect.
- `{ "script": "api/crm/mock.mjs", "port": 4010 }`: your own Node mock, started as
  `node <script> --port <port>`. Use one as soon as the UI needs to see filtering or create/update/delete
  work. Seed it from the spec's examples so spec and mock stay in sync.

Write realistic examples into the spec: the overlay then shows real structures before a backend exists.

## The overlay's data mode

Two tabs in the overlay next to **Selection**:

**Data** – for the selected element:

- **Lineage:** `View → Component → Store → operation (METHOD path) → mapper()` plus spec title and version, for
  every store the component injects. The bridge derives it statically with the workspace's TypeScript compiler:
  `inject()`ed store → calls of the generated client (inside `rxResource` = read, elsewhere = write, with the store
  method that makes it) → operationId in the spec → read mapper (a parameter typed with a generated DTO) and write
  mapper (a generated return type; untyped functions by name, `toX(dto)` / `toXInput(draft)`) → their returned
  object literals. When the element's data comes in through inputs (a row component, an AG Grid cell), the view is
  the element's component and the store sits in an outer one.
- **Mapping table:** UI label ↔ model field ↔ API field, with the conversion on read and on write. Lookup tables
  (`STATUS[dto.state]`) are expanded (`ACTIVE → Aktiv …`), the selected value's row is highlighted (AG Grid
  `col-id`, `data-field`, a store read on the element's template line, or its interpolation). Model fields that
  are not shown get **+ Show**, API fields that are not read get **+ Map**, request fields no write mapper sets get
  **+ Map on write** (marked when the spec requires them); clicking a row prefills a "change this mapping" task.
- **Writes:** store method → operation (METHOD path) via the write mapper, or "no write mapper".
- **Forms:** every Reactive or Signal Form of the component. The submit handler's store call leads through the write
  mapper to the request field of every control; its validators (in code and as template attributes) are compared
  with that field's spec constraints. Status per control: ✓ ok, **missing** (the spec requires a validator the
  control lacks), **differs** (e.g. another `maxLength`), **extra** (stricter than the spec), **unmapped** (not
  sent), **no control** (a request field no control writes – a blocker if required). **+ Validator**,
  **+ Control**, **Fix** and **Fix all** prefill the fix. A form whose submit writes to no API shows
  "No API write" and an operation picker.
- **Live:** what the running app does, from the overlay's network capture and the adapter's live state:
  - the last requests per operation of the lineage (status, time, size, item count) with the response's spec
    issues (`required, missing`, `expected integer, got string`, `not one of …`, `null, not nullable`, undocumented
    status; unknown fields as info) and the body. Validation checks types, required, nullable, enums and formats,
    not lengths, ranges or patterns.
  - **Simulate** per operation: Delay 2 s (then the real request), Empty (lists emptied, counts 0, or 204), Error
    500, Error 4xx – built from the spec's responses and examples, answered in the browser without reaching the
    server. Simulations last for the browser tab until switched off; a banner lists them with **Reload page** and
    **Clear all**. Use them to see the store's loading, empty and error states.
  - live state: the selected control (value, valid, touched, dirty, errors), the form and its invalid controls
    (why submit is disabled), the store's signals and resources.
  - real values of the selected item: each model field next to the API values it came from.
  - **Debug with agent** prefills a task; every Data task carries the live state.
- **Tasks:** every Data task carries the lineage and the live state as structured context and goes to the agent
  chosen under _Run with_ (Claude Code or an OpenCode model).
- **Binding unbound elements:** pick a spec and an operation → **Let AI propose a mapping**, or for a write
  operation (POST/PUT/PATCH) **Let AI propose a form**; a form with "No API write" can be bound the same way. The
  agent must not change files; it submits a table via `npx benda proposal .benda/proposal-input.json`. The table appears
  editable in the overlay (forms: label, draft field, API field, conversion, widget, validators, options; empty
  cells filled from the spec); **Implement mapping** / **Implement form** sends the confirmed table as the
  implementation task.

**API** – browse and search specs and versions, add a spec or a new version with a diff against the previous
one, see which version a client is generated from (●) and regenerate it. **Impact on the app** compares two
versions of an API (default: the generated one → the selected or newly added one). The core diffs the specs field
by field (removed, renamed, changed type, required or constraints, new fields and operations), the adapter maps
that onto the code generated from that API, grouped:

- **Breaking:** a mapper reads or sets a field the version removes or renames, or maps or imports a removed
  schema; a store calls a removed or renamed operation, or one whose request or response type changed; a request
  field became required and the write mapper does not set it; a form control writes a removed or renamed field.
- **Changed:** a field the code reads or writes changes its type, required/nullable or constraints – for forms,
  a validator to adjust.
- **New in the API:** fields no mapper reads or writes yet.

**Migrate mapping to \<version\>** sends one task: point the generator config at the version, regenerate, fix the
listed places following these rules, map new fields only where the UI needs them (and list the skipped ones), run
the mapper tests and `npx benda check`.

## Checks

`npx benda check [--json] [--level error|warning|info]` checks the whole workspace against these rules, without
the bridge. It prints `file:line  level  rule  message` with a `fix:` line, and exits 1 when a finding reaches
`--level` (default `error`). Run it after changing mappers, stores or forms, and fix every error before finishing a
data task.

| Rule                   | Level                                   | Finds                                                                  |
| ---------------------- | --------------------------------------- | ---------------------------------------------------------------------- |
| `component-imports-api` | error                                  | a component imports the generated client or its DTOs                   |
| `states-not-rendered`  | warning                                 | a template shows store data but never its `isLoading` or `error`       |
| `mapper-untested`      | info                                    | a mapper without a `.spec.ts`, never called there, or with unchecked fields |
| `write-input-gap`      | error (required), info (optional), warning (no write mapper) | a request field the write mapper does not set |
| `form-validation`      | error (a validator differs, a required validator is missing, a required field has no control), warning (another validator is missing, an optional field has no control), info (extra) | form validators that do not match the request field's spec; controls the submit does not send to an API are not checked |
| `operation-unknown`    | error                                   | a store calls an operation the spec does not define                    |
| `analysis-failed`      | warning                                 | a file that could not be analysed                                      |

## Using it in an existing project

1. Install Benda (`npx ng add @strokkurio/benda-angular`). It adds `api.dir` and an empty `api.mocks` to
   `benda.config.json` and appends these rules to `AGENTS.md`.
2. Point `api.dir` at the spec folder if it is not `api/`. Set `api.generate` if the generator is run by
   a custom command.
3. The API tab works immediately on the existing specs and generator config. Add `api.mocks` and a
   `/api` proxy if you want to work without a backend.
4. Run `npx benda check` to see where the code departs from these rules; add it to CI with the level
   the team agrees on.
